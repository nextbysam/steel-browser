LEARNINGS — Steel Browser + Orb Cloud Integration
===================================================
Last updated: 2026-03-27

## Orb Cloud Platform

- Registration is API-only: POST /api/v1/auth/register with email
- Two-tier keys: initial api_key → create org key with orb_ prefix
- Computers: create → config (upload orb.toml) → build → deploy → agents
- Public URL: https://{first-8-chars-of-id}.orbcloud.dev
- Agent process runs as non-root user (not root from build)
- [agent.env] vars ARE injected into agent process, NOT into exec shell
- ${VAR} syntax in env resolves from org secrets at deploy time
- Exec endpoint has 10s timeout (now deprecated)
- Build steps run sequentially, stop on first failure
- Build and agent run in different security contexts
- Computers can be auto-deleted when agents crash

## Ubuntu 24.04 on Orb

- `apt-get install chromium` installs a SNAP STUB, not real Chromium
- Snap doesn't work in containers/sandboxes
- Use Google Chrome deb: curl + apt-get install ./chrome.deb
- Google Chrome works for Steel Browser but NOT for CRIU checkpoint
- Playwright's Chromium works for CRIU but needs correct browser path

## Steel Browser

- 1 session per container — hardcoded in SessionService.activeSession
- No auth in OSS (issue #235)
- No scaling/clustering in OSS (issue #144, deliberately Cloud-only)
- Husky prepare script breaks builds: use `npm pkg set scripts.prepare='echo noop'`
- DuckDB native module needs scripts during npm install (don't use --ignore-scripts)
- Entry point: api/build/index.js
- CHROME_EXECUTABLE_PATH env var controls which Chrome binary Steel uses
- Steel Cloud runs on Fly.io Machines API
- SDK supports custom baseUrl — users change 1 line to switch backends

## CRIU Checkpoint/Restore

### What works
- Playwright + Chromium (Chrome for Testing 145.0.7632.6)
- Launched from agent process (not exec)
- With --no-sandbox --disable-gpu --disable-dev-shm-usage
- 3 consecutive checkpoint/restore cycles on same VM — all pass
- Cookies, localStorage, DOM state all preserved
- Screenshots identical before/after restore
- Restore time: ~500ms

### What doesn't work
- Google Chrome (via Puppeteer-core): crashpad + zygote + helpers cause
  CRIU restore to hang indefinitely. Different process tree than Playwright.
- Chrome launched via exec endpoint: different security context causes SIGTRAP
- Playwright's chromium_headless_shell from exec: SIGTRAP due to missing
  /proc/self and capability check failures (prctl PR_CAPBSET_READ)

### Key CRIU flags needed
- --ghost-limit (Chrome creates large temp files it deletes but keeps open)
- --file-locks (Chrome holds file locks)
- Both flags needed on BOTH dump AND restore

### Browser path issue
- Build runs as root, installs to /root/.cache/ms-playwright/
- Agent runs as non-root, looks in /home/agent/.cache/
- Fix: PLAYWRIGHT_BROWSERS_PATH=/opt/browsers in both build step AND agent.env

### Agent startup order
- Server MUST start before Chrome (listen on port first)
- Launch Chrome async after server.listen()
- If Chrome crashes during sync init, agent process dies, Orb deletes computer
- Async init: server responds to health immediately, Chrome starts in background

## Orchestrator

- Fastify + @fastify/websocket for CDP proxy
- CommonJS output (not ESM) for Orb compatibility
- SessionRouter maps session IDs to VM URLs
- WarmPool pre-provisions VMs (but each takes 3-5 min to build)
- ContextStore saves cookies/localStorage to disk on session release
- All Steel SDK endpoints proxied transparently
- New endpoints: restoreSessionId, /orchestrator/health, /orchestrator/contexts

## Cost Model

- Orb at 1,000 agents: ~$500/month
- VPS at 1,000 agents: ~$30,000/month (60x more)
- E2B at 1,000 agents: ~$10,000/month (20x more)
- With CRIU: agents that run 5 min/hour cost 1/12th
- At 10,000 agents: $1,000/month vs $300,000 VPS (300x)

## What We Haven't Tested Yet

- Session persistence round-trip (save cookies → restore in new session)
- Concurrent sessions through orchestrator (proven on raw VMs, not orchestrator)
- Playwright-based Steel Browser (Steel uses Puppeteer, would need refactor)
- CRIU with multiple browser tabs
- CRIU with WebSocket connections (likely break on restore)
- Long-duration checkpoint (hours/days, not seconds)
- Warm pool with CRIU (checkpoint idle VMs instead of destroying)

- Repo: github.com/nextbysam/orb-browser

- Server.js must set PLAYWRIGHT_BROWSERS_PATH in code AND orb.toml [agent.env]

## CDP WebSocket Proxy (2026-03-27)

- Orb's HTTPS proxy (nginx) routes HTTP to the container's exposed port
- WebSocket upgrades through the HTTPS proxy DON'T work (wss:// connections fail)
- Direct host port (e.g., 65.108.74.27:40027) is also unreachable (firewall)
- HTTP-based CDP endpoints (/json/version, /json) work through HTTPS proxy
- WebSocket-based CDP (devtools/browser/ID) does NOT work through HTTPS proxy
- This blocks browser-use integration — browser-use needs a WebSocket CDP connection
- Need to ask Orb team to enable WebSocket forwarding on their nginx proxy

## browser-use Integration (2026-03-27)

- browser-use 0.12.5 uses direct CDP (not Playwright)
- Constructor: Browser(cdp_url="http://host:port") — just needs HTTP/WS endpoint
- No special Browserbase integration code — browser-use is provider-agnostic
- The cdp_url is used to discover the WS debugger URL via /json/version
- Then connects via WebSocket to the devtools/browser/ID path
- If WebSocket is blocked, browser-use can't connect

## WebSocket CDP Proxy (2026-03-27) — UNRESOLVED

- Orb nginx returns 101 Switching Protocols for WebSocket upgrade (confirmed via curl -v)
- But actual WebSocket data exchange fails — "no close frame received or sent"
- Tried two proxy approaches:
  1. ws library (message-level proxy) — same failure
  2. Raw TCP pipe (net module) — same failure
- The connection upgrades but data doesn't flow
- Possible causes:
  - Orb nginx might buffer/interfere with WebSocket frames after 101
  - The double-proxy (nginx → our server → Chrome CDP) might cause issues
  - Our server's upgrade handler might conflict with nginx's
- Need to test: expose port 9222 directly without our proxy in the middle
  - If Orb's nginx can proxy WebSocket to 9222 directly, remove our proxy entirely
  - The server.js only needs to provide HTTP endpoints (/health, /json/version, /set-host)
  - WebSocket goes nginx → Chrome directly on port 9222

## browser-use + Orb Cloud — VERIFIED (2026-03-27)

- browser-use 0.12.5 connects via CDP WebSocket — just needs a wss:// URL
- URL pattern: wss://{id}.orbcloud.dev/_port/9222/devtools/browser/{guid}
- Chrome binds to 127.0.0.1 only — need TCP proxy on 0.0.0.0:9222 → 127.0.0.1:9223
- Orb _port/9222 proxy routes external traffic to container 9222
- /set-host endpoint needed to set public hostname (Orb doesn't pass it in headers)
- /cdp endpoint returns the full wss:// URL for browser-use
- Full flow verified: connect → navigate Google → sleep → wake → still on Google → navigate again
- WebSocket drops on checkpoint (expected) — browser-use must reconnect after wake
- Browser ID stays the same across checkpoint/restore (same /cdp URL works)
